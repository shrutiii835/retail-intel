# DATA DICTIONARY

Conventions used throughout:

- `*_key` — integer **surrogate** key, generated by the pipeline, never seen by
  the business. `-1` = Unknown member, `0` = No Campaign.
- `*_id` — **natural / business** key, as it exists in the source system.
- `_`-prefixed columns are lineage/audit metadata, not business data. They are
  dropped before the Power BI export.
- Bronze stores **every column as STRING** on purpose (see
  [ARCHITECTURE.md](ARCHITECTURE.md) §4). Types below apply from Silver onward.

## Source feeds

### sales (POS transaction log)

| Field | Type | Source | Validation | Business meaning |
|---|---|---|---|---|
| `transaction_id` | STRING | POS | SAL_001 not null; **business key** | Uniquely identifies one till transaction line |
| `transaction_timestamp` | TIMESTAMP | POS | SAL_004 parses; SAL_011 in period | When the sale occurred |
| `product_id` | STRING | POS | SAL_002 not null; SAL_012 exists | What was sold |
| `store_id` | STRING | POS | SAL_003 not null; SAL_013 exists | Where it was sold |
| `quantity` | INT | POS | SAL_005 whole number; SAL_006 > 0 | Units sold on this line |
| `unit_price` | DECIMAL(12,2) | POS | SAL_007 parses; SAL_008 ≥ 0 | Actual selling price before discount |
| `discount_amount` | DECIMAL(12,2) | POS | SAL_009 ≥ 0; SAL_010 ≤ gross | Total discount on this line |
| `campaign_id` | STRING | POS | SAL_014 resolves (repair) | Promotion attributed to the sale; blank = not promoted |
| `last_modified_timestamp` | TIMESTAMP | POS | — | **Watermark column.** Equals sale time, or later if corrected |

### inventory (weekly stock snapshot)

| Field | Type | Validation | Business meaning |
|---|---|---|---|
| `inventory_id` | STRING | INV_001 not null | Snapshot row identifier |
| `snapshot_date` | DATE | INV_002 parses; **part of business key** | Sunday of the snapshot week |
| `product_id` | STRING | INV_003, INV_007 | Product counted |
| `store_id` | STRING | INV_004, INV_008 | Store counted |
| `stock_quantity` | INT | INV_005 whole; INV_006 ≥ 0 | Units on hand. **Semi-additive** — never sum across dates |
| `last_modified_timestamp` | TIMESTAMP | — | Watermark column |

### campaigns (promotion master)

| Field | Type | Validation | Business meaning |
|---|---|---|---|
| `campaign_id` | STRING | CAM_001; **business key** | Promotion identifier |
| `campaign_name` | STRING | — | Human-readable name |
| `product_id` | STRING | CAM_007 exists | The single promoted product |
| `start_date` / `end_date` | DATE | CAM_002/003 parse; **CAM_004 end ≥ start** | Inclusive promotion window |
| `discount_percentage` | DECIMAL(5,2) | CAM_005 in 0–100 | Advertised discount depth |
| `campaign_cost` | DECIMAL(12,2) | CAM_006 ≥ 0 | Total spend. **The ROI denominator** |
| `last_modified_timestamp` | TIMESTAMP | — | Watermark column |

### products / stores (masters)

`product_id`, `product_name`, `category`, `sub_category`, `brand`, `unit_cost`
(PRD_003), `list_price` (PRD_004, and **PRD_005 ≥ unit_cost**).

`store_id`, `store_name`, `city`, `state`, `region`, `store_format`
(Hypermarket / Supermarket / Express), `open_date`.

## Silver — derived business columns

Beyond the typed source fields:

| Field | Table | Derivation | Why it lives here |
|---|---|---|---|
| `transaction_date` | sales | `to_date(transaction_timestamp)` | Join key to `dim_date` |
| `gross_amount` | sales | `quantity × unit_price` | Line total before discount |
| **`net_revenue`** | sales | `gross_amount − discount_amount` | **The single definition of revenue** (D12). Gold and Power BI carry it forward rather than recomputing |
| `campaign_id` | sales | resolved id, or `NONE` / `UNKNOWN` | Never null, so the Gold join can be INNER |
| `campaign_resolved` | sales | `false` when the id could not be resolved | Makes repaired attribution measurable |
| `gross_margin_pct` | products | `(list_price − unit_cost) / list_price` | Product-level margin |
| `duration_days` | campaigns | `datediff(end, start) + 1` | Inclusive length; the ROI baseline scalar |

Lineage: `_silver_run_id`, `_silver_processed_at`.

**Quarantine tables** additionally carry `_dq_failed_rules` (array),
`_dq_failed_rules_csv`, `_dq_run_id`, `_dq_batch_id`, `_quarantined_at`.

## Gold — dimensions

### dim_date (182 rows)

`date_key` (INT `yyyyMMdd`, PK), `date`, `year`, `quarter`, `month`,
`month_name`, `year_month`, `year_month_label`, `day_of_month`, `day_of_week`,
`day_name`, `week_of_year`, `is_weekend`.

> `date_key` is an integer rather than an arbitrary sequence: it joins as fast as
> any surrogate, sorts chronologically, and is readable in a query result, which
> makes debugging a join far easier.

### dim_product (221 rows = 220 + Unknown)

`product_key` (PK), `product_id`, `product_name`, `category`, `sub_category`,
`brand`, `unit_cost`, `list_price`, `gross_margin_pct`, `_row_hash`.

### dim_store (29 rows = 28 + Unknown)

`store_key` (PK), `store_id`, `store_name`, `city`, `state`, `region`,
`store_format`, `open_date`, `_row_hash`.

### dim_campaign (38 rows = 36 + No Campaign + Unknown)

`campaign_key` (PK), `campaign_id`, `campaign_name`, `product_id`, `start_date`,
`end_date`, `discount_percentage`, `campaign_cost`, `duration_days`, `_row_hash`.

| Key | `campaign_id` | Meaning |
|---:|---|---|
| `0` | `NONE` | Genuinely not promoted |
| `-1` | `UNKNOWN` | Source supplied an id we could not resolve |
| `> 0` | real id | A real campaign |

> `_row_hash` is a SHA-256 of the attribute columns, used to skip MERGE updates
> for unchanged rows so the "rows updated" figure stays meaningful.

## Gold — facts

### fact_sales (130,023 rows)

**Grain: one sales transaction.** PK `transaction_id` (degenerate dimension).

| Field | Type | Meaning |
|---|---|---|
| `transaction_id` | STRING | PK, degenerate dimension |
| `date_key` | INT | FK → `dim_date` |
| `product_key` | INT | FK → `dim_product` |
| `store_key` | INT | FK → `dim_store` |
| `campaign_key` | INT | FK → `dim_campaign` |
| `transaction_timestamp` | TIMESTAMP | Exact sale time |
| `transaction_date` | DATE | Sale date |
| `year_month` | INT | **Partition column** (`yyyyMM`) |
| `quantity` | INT | Units — additive |
| `unit_price` | DECIMAL(12,2) | Price per unit — **non-additive**, never sum |
| `gross_amount` | DECIMAL(14,2) | Before discount — additive |
| `discount_amount` | DECIMAL(12,2) | Discount — additive |
| `net_revenue` | DECIMAL(14,2) | **The revenue measure** — additive |
| `cogs` | DECIMAL(14,2) | `quantity × unit_cost` — additive |
| `gross_profit` | DECIMAL(14,2) | `net_revenue − cogs` — additive |
| `is_promoted` | BOOLEAN | `campaign_key > 0` |
| `campaign_resolved` | BOOLEAN | `false` for the 198 repaired rows |
| `last_modified_timestamp` | TIMESTAMP | MERGE guard — only newer rows overwrite |

### fact_inventory_snapshot (74,800 rows)

**Grain: one product, one store, one weekly snapshot date.**
PK `(date_key, product_key, store_key)`. **Periodic snapshot fact.**

| Field | Type | Meaning |
|---|---|---|
| `date_key`, `product_key`, `store_key` | INT | Composite PK / FKs |
| `snapshot_date` | DATE | Snapshot date |
| `year_month` | INT | Partition column |
| `inventory_id` | STRING | Source identifier |
| `stock_quantity` | INT | Units on hand — **semi-additive** |
| `stock_value_at_cost` | DECIMAL(16,2) | `stock_quantity × unit_cost` — **semi-additive**. Valued at cost so it is comparable with COGS in the turnover ratio |

> **Semi-additive** means: sum across products and stores, **average** across
> dates. Summing 17 weekly snapshots would count the same physical units 17
> times.

### mart_campaign_roi (36 rows)

**Grain: one campaign.** Precomputed because the baseline window sits outside
the report's filter context (D11).

Key fields: `campaign_cost`, `campaign_revenue`, `campaign_units`,
`campaign_gross_profit`, `baseline_window_days` (28), `baseline_daily_revenue`,
`expected_baseline_revenue`, `incremental_revenue`, `incremental_units`,
`incremental_gross_profit`, `roi`, `roi_margin_based`, `uplift_pct`,
`is_profitable`.

| Measure | Formula |
|---|---|
| `expected_baseline_revenue` | `baseline_daily_revenue × duration_days` |
| `incremental_revenue` | `campaign_revenue − expected_baseline_revenue` |
| `roi` | `(incremental_revenue − campaign_cost) ÷ campaign_cost` |
| `roi_margin_based` | `(incremental_gross_profit − campaign_cost) ÷ campaign_cost` |

> Both ROIs are exposed because they disagree sharply: +0.42 on revenue,
> −1.00 on margin. See [METRICS.md](METRICS.md) M7.
