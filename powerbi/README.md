# Power BI — build guide

Everything the report needs is already generated, including a **pre-built
semantic model**. This guide is mechanical: follow it and you get the four-page
dashboard the project claims.

---

## Read this first — the platform constraint

**Power BI Desktop is Windows-only.** Microsoft does not ship a macOS build, and
a `.pbix` file embeds a *compiled* tabular database that only the Analysis
Services engine can write — so it cannot be generated by a script on any
platform.

What *has* been generated is a **PBIP project** (`RetailIntel.pbip`), Power BI's
text-based project format. The entire model is already built:

| | |
|---|---:|
| Tables | 7 + `_Measures` |
| Columns, explicitly typed | 94 |
| Relationships | 8 |
| DAX measures | 40 |
| Report pages | 4 (named, empty) |

`dim_date` is already marked as the date table, surrogate keys on the facts are
already hidden, and `mart_campaign_roi` is deliberately joined only to
`dim_campaign` — so the three mistakes that cost people an afternoon are already
avoided.

**Your options, in order of effort:**

1. **Any Windows machine** — work laptop, a friend's, a lab PC. Copy the repo
   across, open `RetailIntel.pbip`, point the `DataFolder` parameter at the CSVs,
   refresh, and place visuals. ~20 minutes.
2. **Windows VM on the Mac** — Parallels (paid) or UTM (free, slower). Same
   steps once Windows is up.
3. **Microsoft Fabric, browser only** — works on macOS. Create a Fabric trial
   workspace, connect it to a Git repo containing this PBIP, and Fabric
   materialises the semantic model and report server-side. No Windows needed,
   but it needs a Fabric trial and Git setup.

### Why the report pages are empty

Hand-authoring Power BI's visual-container JSON is fragile and **cannot be
validated without Power BI Desktop**, which does not run on the machine this was
generated on. A malformed report definition stops the *whole project* from
opening — strictly worse than no visuals. The model is the part that takes an
hour by hand; placing visuals on a finished model takes twenty minutes and is
the enjoyable part.

Regenerate the project any time with:

```bash
.venv/bin/python scripts/build_pbip.py
```

## Opening the PBIP (Windows)

1. Copy the repo (or just the `powerbi/` folder) to the Windows machine.
2. In Power BI Desktop: **File → Options and settings → Options → Preview
   features → tick "Power BI Project (.pbip) save format"**, then restart.
3. **File → Open** → `powerbi/RetailIntel.pbip`.
4. **Home → Transform data → Manage parameters →** set `DataFolder` to the full
   path of `powerbi\data\`, **including the trailing backslash**, e.g.
   `C:\RetailIntel\powerbi\data\`.
5. **Close & Apply.** The model loads all seven tables with types,
   relationships and measures already in place.
6. Skip to **step 4 — Build the four pages** below. Steps 1–3 are only needed if
   you are building from the CSVs by hand instead.

> If the trailing backslash is missing, every table fails with "file not found" —
> the parameter is concatenated directly onto the filename.

## Building from scratch instead (any route)

If the PBIP does not open for any reason, the steps below rebuild the same
thing manually from the CSVs. Nothing is lost — the measures are all in
`measures.dax`.

## 1. Load the data

1. Open **Power BI Desktop** → **Get data** → **Text/CSV**.
2. Load all seven files from `powerbi/data/`.
3. In **Transform data** (Power Query), check the data types on each table —
   Power BI usually infers these correctly, but confirm:
   - all `*_key` columns → **Whole number**
   - `date`, `snapshot_date`, `start_date`, `end_date`, `open_date` → **Date**
   - `net_revenue`, `unit_price`, `cogs`, `gross_profit`, `campaign_cost`,
     `stock_value_at_cost` → **Decimal number**
   - `transaction_id`, `product_id`, `store_id`, `campaign_id` → **Text**
   - `is_promoted`, `campaign_resolved`, `is_weekend`, `is_profitable` → **True/False**
4. **Close & Apply.**

> `date_key` is an integer like `20250312`. Keep it as a whole number — it is the
> join key. Use the separate `date` column for anything date-shaped.

---

## 2. Build the model

Go to **Model view** and create these relationships. All are
**one-to-many**, single direction, from the dimension to the fact.

| From (one side) | To (many side) | Active |
|---|---|---|
| `dim_date[date_key]` | `fact_sales[date_key]` | Yes |
| `dim_product[product_key]` | `fact_sales[product_key]` | Yes |
| `dim_store[store_key]` | `fact_sales[store_key]` | Yes |
| `dim_campaign[campaign_key]` | `fact_sales[campaign_key]` | Yes |
| `dim_date[date_key]` | `fact_inventory_snapshot[date_key]` | Yes |
| `dim_product[product_key]` | `fact_inventory_snapshot[product_key]` | Yes |
| `dim_store[store_key]` | `fact_inventory_snapshot[store_key]` | Yes |
| `dim_campaign[campaign_key]` | `mart_campaign_roi[campaign_key]` | Yes |

**Connect `mart_campaign_roi` to `dim_campaign` only.** It also carries a
`product_key`, and it is tempting to join that to `dim_product` — do not. That
would create a loop (`dim_product → fact_sales → dim_campaign → mart →
dim_product`), and Power BI would deactivate one relationship at random. The
mart already carries `product_name`, `category` and `brand` as columns, so use
those directly.

Then:

1. Select `dim_date` → **Table tools ▸ Mark as date table** → choose
   `dim_date[date]`. The time-intelligence measures return wrong answers
   without this, and they fail silently.
2. Hide the technical columns from report view (right-click ▸ Hide): every
   `*_key` column on the fact tables, plus `year_month` on the facts.

---

## 3. Add the measures

1. **Home ▸ Enter data** → create an empty table named `_Measures` → Load.
2. Open `powerbi/measures.dax` and add each measure
   (**Modeling ▸ New measure**), with `_Measures` selected.
3. Delete the placeholder `Column1` from `_Measures`.
4. Set format strings as noted at the top of the `.dax` file.

## Why CSV and not a live Delta connection?

Power BI Desktop cannot read a Delta table from a local folder — the Delta
connector targets Databricks and Fabric. Pointing Power BI at the raw Parquet
files underneath would read *every* version in the transaction log rather than
the current snapshot, silently inflating every total.

In a real deployment the report would connect to **Databricks SQL** with the
native connector, which understands Delta and needs no export step. That is
avoided here on purpose: it requires a running SQL warehouse, which costs money
for as long as the report is open. See `DECISIONS.md` and `AZURE_CLEANUP.md`.
